# Спецификация доработки standalone-редактора

## 1. Назначение

Standalone-редактор должен открывать каталог проекта с Lua-файлами без
запущенного EPLAN, позволять редактировать технологические объекты и сохранять
результат. Ошибки данных проекта должны быть доступны пользователю в отдельном
журнале и не должны маскироваться потоком служебных исключений отладчика.
Редактор также должен находить проекты в настраиваемых репозиториях и открывать
существующую форму настройки межпроектного обмена для выбранной пары проектов.

Документ одновременно является спецификацией и журналом выполнения работ.
После каждой доработки таблица в разделе 6 должна обновляться фактическим
результатом и способом проверки.

## 2. Исходное состояние

В предоставленном `debuglog.txt` зафиксировано 735 first-chance исключений:

- 678 `System.Exception` из основной сборки;
- 56 `System.ArgumentException` из `mscorlib`;
- 1 `System.IO.FileNotFoundException` из основной сборки;
- необработанных исключений и аварийного завершения нет, процесс завершился с
  кодом 0.

Основной поток `System.Exception` создавался внутри
`ParamOperationsProperty.SetNewValue()` при обычной проверке неизменного или
некорректного значения. `ArgumentException` создавались вызовами `Enum.Parse`
для пустых типов и подтипов. Дополнительно standalone-загрузчик не использовал
поля `dtype` и `subtype` из `main.io.lua`, поэтому устройства загружались с
типом `NONE`, а неоднозначные имена наподобие `SAFETYDI1` не распознавались.

Единичное `FileNotFoundException` в логе не содержит стека вызовов. Оно не
является необработанным и предположительно связано с поиском ресурса CLR.
Окончательная классификация требует повторного запуска исходного проекта с
включённым стеком first-chance исключения.

## 3. Функциональные требования

### 3.1. Загрузка устройств

1. Загрузчик обязан читать `name`, `descr`, `article`, `dtype` и `subtype` из
   таблицы `devices` файла `main.io.lua`.
2. Числовая пара `dtype`/`subtype` должна преобразовываться в
   `DeviceType`/`DeviceSubType` по принятой формуле
   `dtype * DSTExt.TypeMultiplier + subtype`.
3. Тип из `dtype` должен использоваться для разбора неоднозначных имён
   устройств. Сохраняемое внутреннее имя при этом не должно изменяться.
4. Неизвестные устройства и подтипы должны попадать в журнал проекта, но не
   должны прерывать загрузку остальных данных.
5. Исходный `main.io.lua` должен сохраняться без регенерации, так как узлы,
   модули и каналы в standalone-режиме пока не восстанавливаются полностью.

### 3.2. Исключения при проверке данных

1. Ожидаемый отрицательный результат валидации не должен реализовываться через
   генерацию и перехват исключения.
2. Неизменное, пустое, некорректное или выходящее за диапазон значение списка
   операций должно возвращать `false` без изменения модели.
3. Неизвестное строковое значение типа или подтипа должно приводить к `NONE`
   без `ArgumentException`.
4. Реальные ошибки Lua, файловой системы и модели должны сохранять стек вызовов
   в журнале проекта.

### 3.3. Журнал проекта

1. Для каждого открытого проекта должен создаваться журнал
   `standalone_project_errors.log` в каталоге проекта.
2. Файл должен пополняться между сеансами; начало сеанса отмечается датой и
   временем.
3. Одинаковые сообщения в рамках текущей операции не должны дублироваться.
4. Текущий журнал должен открываться из пункта меню `Файл -> Журнал проекта`.
5. В названии пункта меню должно отображаться количество сообщений текущей
   операции.
6. Окно должно поддерживать вывод текста, прогресс операции и блокировку кнопки
   закрытия во время сохранения.
7. Ошибка записи самого журнала не должна завершать приложение.
8. Необработанные исключения UI- и фоновых потоков должны записываться как в
   журнал проекта, так и в аварийный `standalone_error.log` приложения.

### 3.4. Репозитории проектов

1. Репозиторий проекта задаётся путем к корневой папке.
2. Проектами считаются только непосредственные подпапки репозитория.
3. Подпапка считается корректным проектом, если в ней есть `main.io.lua` с
   непустым `PAC_name`.
4. Пользователь должен иметь возможность добавлять, удалять и обновлять
   репозитории через меню `Проекты -> Репозитории проектов`.
5. Список репозиториев должен сохраняться между запусками в
   `%LocalAppData%\EasyEPlanner.StandaloneEditor\project_repositories.txt`.
6. Недоступный репозиторий или некорректная подпапка не должны блокировать
   сканирование остальных папок; количество ошибок структуры показывается в
   окне настройки.
7. Обнаружение проектов не должно изменять Lua-файлы.

### 3.5. Редактор межпроектного обмена

1. Редактор открывается из меню `Проекты -> Межпроектный обмен`.
2. Перед открытием пользователь выбирает главный и второй проект из общего
   списка проектов репозиториев.
3. Текущий открытый standalone-проект, если он корректен, предлагается как
   главный даже до добавления его корневой папки в репозитории.
4. Проекты с одинаковым `PAC_name` нельзя выбрать как пару, поскольку
   `PAC_name` является идентификатором модели обмена.
5. Данные устройств читаются из `main.io.lua`, существующие связи — из
   `shared.lua`. При сохранении изменяется только `shared.lua` каждого
   участвующего проекта.
6. Выбранный второй проект должен быть активен при первом показе существующей
   формы межпроектного обмена.
7. Запуск из standalone не должен обращаться к открытому проекту EPLAN или
   вызывать синхронизацию через EPLAN API.
8. В standalone-сеансе загружаются только выбранные два проекта. Упомянутые в
   `shared.lua` сторонние проекты остаются незагруженными, чтобы сохранение не
   изменило их файлы.
9. Путь сохранения должен корректно поддерживать как исторический путь к корню
   репозитория, так и непосредственный путь к папке проекта.
10. Новый `shared.lua` должен получать кодировку из `main.objects.lua`, затем из
   `main.io.lua`; при отсутствии обоих файлов используется UTF-8.
11. Standalone-вход не должен создавать `EProjectManager`, обращаться к
    `ProjectManager` или требовать сборки `Eplan.EplApi.*`.

## 4. Нефункциональные требования

- Изменения общей модели не должны менять публичное поведение add-in в EPLAN.
- Новые комментарии и документация пишутся на русском языке.
- Standalone-редактор и тестовый проект должны собираться под .NET Framework
  4.7.2 для x64.
- Ошибки одного устройства не должны препятствовать загрузке остальных.
- Файл проекта `main.io.lua` не должен изменяться при одном только открытии.

## 5. Критерии приёмки

1. Сборка `EasyEPlanner.StandaloneEditor.csproj` в конфигурации Debug проходит.
2. Набор тестов `ParamOperationsPropertyTest` проходит, включая проверку
   отсутствия first-chance исключений.
3. Тест загрузчика восстанавливает `SAFETYDI1` как `DeviceType.DI` и
   `DeviceSubType.DI`.
4. Тест журнала подтверждает запись сообщения в файл, исключение дубля и
   очистку сообщений текущей операции.
5. При повторной ручной отладке проекта из `debuglog.txt` отсутствуют массовые
   `System.Exception` и `ArgumentException`, описанные в разделе 2.
6. Все обнаруженные отклонения и ограничения заносятся в раздел 7.
7. Тест менеджера репозиториев подтверждает сохранение списка, обнаружение
   проекта по `PAC_name` и отсутствие рекурсивного сканирования.
8. Тесты существующего межпроектного обмена проходят без регрессий.
9. Standalone-сборка содержит пункты меню управления репозиториями и выбора
   пары проектов.

## 7. Ограничения и последующие этапы

### 7.1. Обязательная ручная проверка

Следует повторно открыть исходный проект под отладчиком Visual Studio и
сохранить новый журнал Output с включённым стеком для first-chance
`FileNotFoundException`. Массовые исключения из раздела 2 после исправлений не
ожидаются.

### 7.2. Полное восстановление `main.io.lua`

Текущая версия загружает данные устройств, необходимые редактору объектов, но
не восстанавливает узлы, модули, каналы, параметры и свойства. До реализации
полной модели файл сохраняется из исходного текста. При следующей итерации
нужны отдельные загрузчики и тесты round-trip без потери данных.

### 7.3. Результат сохранения

Общий `ProjectDescriptionSaver.Save()` перехватывает исключения и не возвращает
признак успеха. Поэтому главное окно не может надёжно отличить успешное
сохранение от ошибки, записанной во внутренний журнал. Следующая доработка
должна добавить типизированный результат сохранения без нарушения вызовов из
EPLAN.

### 7.4. Изоляция от EPLAN API

Основная сборка по-прежнему содержит ссылки на EPLAN API. Для полностью
переносимого standalone-приложения следует выделить модель и сохранение Lua в
отдельную библиотеку, не зависящую от `Eplan.EplApi.*`.

### 7.5. Дубликаты `PAC_name`

Один `PAC_name` может физически встретиться в нескольких репозиториях. Такие
каталоги отображаются отдельно, но не могут быть выбраны одновременно. Для
автоматического разрешения связей из `shared.lua` используется последний
проиндексированный каталог с этим `PAC_name`; явно выбранные два каталога имеют
приоритет. В следующей итерации можно добавить отдельную диагностику
дубликатов в окно репозиториев.
